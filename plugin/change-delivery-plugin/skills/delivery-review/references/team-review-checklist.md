# 团队 Review 清单

## 审查顺序

1. 对照已批准需求和设计确认范围、行为和兼容性。
2. 检查正确性、边界、错误处理、安全、数据一致性和并发。
3. 检查是否复用现有结构，是否出现重复 Service、DTO、配置、工具或测试夹具。
4. 检查性能，包括 N+1、ORM 懒加载、循环内 IO、逐条写入、无界加载和重复远程调用。
5. 检查测试是否覆盖真实风险以及变更影响的上下游路径。
6. 最后检查工具无法自动处理的可维护性问题，不把格式争论当作关键问题。

## 分级映射

- **必须修复**：安全漏洞、数据丢失、重复扣费、逻辑错误、恢复失败、任务卡死、资源耗尽或确定性测试缺口。映射为 `critical` 或 `important`。
- **建议修改**：当前不导致错误，但会放大负载、降低可维护性或增加恢复风险。只有当前门禁策略要求时才作为可执行 `important`，否则记录为非阻塞观察。
- **仅供参考**：命名、替代写法或未来规模优化，映射为 `minor`，不能阻止通过。

每条 finding 都应说明代码证据、触发条件、影响和建议方向。无法在当前代码路径中证明的问题，应明确说明未发现证据，不得为了显得严格而编造问题。
