# 团队开发规则

## 复用与结构

- 修改前搜索相近实现、公共工具、Service、Repository、DTO、配置、异常类型和测试夹具；优先扩展或组合现有能力。
- 遵守项目既有分层、命名、依赖方向、事务、缓存、日志、序列化和配置读取方式，不创建功能重复的平行实现。
- 改动保持在已批准范围内，避免无关重构、全局格式化、目录迁移和依赖升级。

## 数据与性能

- 涉及数据库表、迁移、ORM Model 或 Entity 时，为新表补充表注释，为新增业务字段补充符合项目习惯的字段注释；索引、唯一约束和状态字段应说明业务含义。
- 检查循环中的数据库、缓存、远程调用、文件 IO 和昂贵计算，避免 N+1、ORM 隐式懒加载、逐条提交和重复扫描。
- 可以批量处理时优先使用批量查询、批量写入、集合映射或分页分批；必须逐条处理时记录锁、幂等、失败隔离或限流方面的理由。

## 中文与编码

- 新增的日志、错误提示、代码注释和开发文档优先使用自然中文，变量、类型、接口、命令和错误码等技术标识保留英文。
- 新增或修改的中文文件使用 UTF-8；发现乱码时先确认文件和终端编码，不在乱码基础上继续编辑。
- 文字描述忠实记录事实，避免“全面解决”“显著提升”等无法验证的结论。

## 开发记录

当项目已有开发记录或架构决策目录，按既有方式更新；没有明确要求时不擅自新增一套文档体系。记录应包含背景、主要修改、复用与取舍、影响范围、实际验证和残留风险。
