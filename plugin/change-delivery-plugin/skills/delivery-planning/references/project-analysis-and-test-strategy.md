# 项目分析与测试策略

## 代码依据

- 以代码为准。README、OpenAPI、历史设计和旧测试只能作为线索，不能替代当前入口、路由、DTO、Service、Repository、任务和配置代码。
- 先识别已有分层、公共能力、状态枚举、错误处理、事务、缓存和测试夹具，再决定新增或扩展位置。
- 按业务链路描述变更，不按文件列表机械拆分。明确入口、状态变化、异步边界、数据来源、外部依赖和最终可观察结果。
- 对不确定事实明确标为待确认项，不得用想象补全产品决策或运行环境。

## 测试设计

- 为每条成功标准定义可执行验证，并区分单元测试、集成测试、接口 E2E、测试环境验收和人工专项检查。
- 明确哪些断言是确定性的。依赖真实网页、AI 判断、第三方最终结果、真实邮件收件或人工支付的结果，不能作为稳定主门禁。
- 异步链路要写清任务入口、队列或调度器、轮询方式、成功和失败终态、最大等待边界以及日志或数据证据。
- 外部依赖必须明确采用真实沙箱、mock、本地替身还是人工步骤，并记录成本、不可重复性和安全风险。
- 需要临时数据时，设计运行标记、资源台账、精确清理方式和清理失败处理；优先使用公开接口，不把数据库直写作为默认方案。

## 设计产物要求

`design.md` 和 `implementation-plan.md` 应说明复用点、影响范围、兼容性、测试策略、回滚或停止条件，以及无法自动覆盖的残留风险。测试资产建设只有在需求或方案明确包含时才进入实施计划。
