# Change Delivery Plugin 共享版本分发设计

## 目标

将当前仅适用于 `C:\Users\ExampleUser` 的个人插件改造成可由不同 Windows
用户安装、升级和卸载的共享版本，并通过私有 Git 仓库和 Codex 团队
Marketplace 分发。首个共享版本面向 Codex CLI，保留现有审批、安全边界和
`READY_TO_MERGE` 终止语义。

## 已选方案

采用“私有 Git 仓库 + 显式引导安装器 + Git-backed Marketplace”方案。

不采用单纯复制 ZIP：它缺少版本、升级和来源追踪。不采用仅执行
`codex plugin add`：当前插件包含 Python 编排运行时，Marketplace 安装不会替用户
隐式创建并信任 Python 虚拟环境。公开 Universal Plugin Directory 留作后续阶段，
本次不扩大到公开发布和公共许可证治理。

## 发布物边界

Git 仓库包含：

- `plugin/change-delivery-plugin` 下的 `.codex-plugin/plugin.json` 和全部技能；
- Python 编排运行时、schema 和受信任 PowerShell 主机；
- 面向接收方的一键安装、升级、诊断和卸载入口；
- `.agents/plugins/marketplace.json` 团队 Marketplace 描述；
- README、兼容性要求、安全边界和版本升级说明；
- 自动化测试，但不把开发测试目录复制进 Codex 的已安装插件目录。

不发布或复制：

- 项目注册表、运行记录、审批文件和本地调度状态；
- GitHub token、Codex 登录信息、SSH key 或其他凭据；
- ExampleProject 等个人项目的绝对路径和环境配置；
- `.git`、pytest 临时目录、worktree 及开发缓存。

仓库默认创建为私有仓库。`UNLICENSED` 在私有团队分发阶段保留，表示未授予
公开再分发许可；若以后公开发布，再单独选择许可证并补充公开发布材料。

## 安装布局

所有路径从 Windows Known Folder 的当前用户目录派生，并验证 `USERPROFILE` 与
Known Folder 一致。禁止把用户名或源码克隆路径当作固定信任锚。

```text
%USERPROFILE%\plugins\change-delivery-plugin\
  .codex-plugin\
  skills\

%USERPROFILE%\.codex\change-delivery\
  bin\
    change-delivery.ps1
  runtime\
    venv\
  host\
    scripts\
  projects\
  runs\
  logs\
  state\
```

插件目录仍采用普通目录和原子替换，不使用 Junction。Python 运行时安装到专用
venv，不污染系统 Python。稳定启动器从 `bin` 调用 venv 中的
`python -m change_delivery`；技能只调用稳定启动器。计划任务固定执行已安装 host
中经哈希锚定的 `run-tick.ps1`，两者都不依赖 Git clone 目录。

## 安装与升级流程

接收方克隆指定 tag 后运行 `scripts/install-shared-plugin.ps1`。安装器按顺序：

1. 验证 Windows、PowerShell、Codex CLI 和 Python 3.12+；
2. 验证源码根、manifest、发布白名单和所有路径均不是链接或 reparse point；
3. 在临时目录创建 venv 并安装当前源码及锁定范围内的运行依赖；
4. 对新运行时执行 `--help` 烟雾测试；项目登记后再用 `doctor --json` 验证项目绑定；
5. 原子发布稳定启动器、受信任主机和技能插件目录；
6. 从已配置的 Marketplace 安装或刷新 `change-delivery-plugin`；
7. 每个 host、venv 和技能发布阶段保留旧版本备份直到该阶段验证成功，阶段切换失败时恢复旧版本；
8. 输出“新建 Codex CLI 会话”的明确提示。

安装器默认作用于当前用户，不需要管理员权限。它不得读取或复制 Codex/GitHub
凭据。依赖下载或 GitHub 登录由各自工具的标准认证机制处理。

升级使用相同入口和语义化版本/tag。Marketplace 固定引用 tag，不跟随可变分支。
卸载入口只删除由 manifest 记录的插件、启动器、venv 和计划任务；默认保留项目
注册表与历史 run，只有显式 `-PurgeData` 才允许删除数据，并在执行前展示目标。

## Marketplace 与 Git 发布

仓库提供 `.agents/plugins/marketplace.json`，名称固定为团队可识别的稳定名称。
Codex CLI 把 Git 仓库以 `owner/repo --ref <tag>` 注册为 Marketplace；目录内的
插件条目使用 `local` source 指向 `./plugin/change-delivery-plugin` 白名单树。
这样固定 Git tag 的同时，不会让 Codex 递归读取运行时、测试或 worktree 元数据。

首次目标为 GitHub 账户 `708828375` 下的私有
`change-delivery-plugin` 仓库；最终 URL 在远端创建或确认后写入 Marketplace。
本机当前 GitHub CLI 认证无效，因此上传前必须由用户重新登录，不能复用或写入
任何 token。

团队成员流程为：克隆仓库或 Marketplace、运行共享安装器、在 `/plugins` 中确认
启用、开启新会话，再显式调用 `$change-delivery`。

## 项目与用户数据隔离

每位用户首次使用时独立注册项目。项目 ID 可以相同，但 repo 路径、测试分支、
版本端点、验收命令和 GitHub 仓库均来自该用户本地配置。升级插件不能覆盖这些
文件。

运行目录继续按 run-id 隔离。日志和对外错误输出不得包含认证信息；发布仓库只
包含模板和 schema，不包含任何真实项目配置。

## 安全与失败处理

- 继续拒绝路径中的链接、reparse point、身份不符的插件目录和非预期发布内容；
- 发布采用同目录 staging、验证、原子切换和可恢复 backup；
- 计划任务固定调用已安装 host 中经哈希锚定的 `run-tick.ps1`，不执行克隆目录中的可变脚本；
- 共享安装器不自动创建公开仓库、不自动变更仓库可见性；
- Git push 前检查 remote、目标账户、分支、提交和仓库可见性；
- Marketplace tag、manifest version 和 Python package version 必须一致；
- 任一步失败都返回非零退出码并保留用户数据；host、venv、launcher 与技能目录各自
  原子切换和阶段内回滚。已经完成验证并切换的阶段保持新版本，重新运行安装器可
  幂等续装；Marketplace 切换失败时恢复安装前的本地快照。

## 测试与验收

实现采用 TDD，并至少覆盖：

1. 非 `JoySun` 用户目录下的安装路径推导；
2. 用户目录含空格和非 ASCII 字符；
3. 链接/reparse point、伪造 USERPROFILE、意外目标目录和越界删除攻击；
4. 首次安装、重复安装、版本升级、失败回滚和保留数据卸载；
5. venv 创建、依赖安装失败以及启动器 smoke test；
6. Marketplace schema、Git URL、tag 与三个版本号的一致性；
7. 插件官方 validator、skill validator、完整 pytest；
8. 干净临时用户环境的安装模拟，以及当前用户环境的受控 smoke test；
9. 发布树不包含凭据、个人配置、`.git` 或测试缓存；
10. 新 Codex CLI 会话中能看到技能并执行 `doctor --json`。

只有上述验证通过，才允许创建发布 tag 和推送。远端创建、认证或推送失败不回滚
已经验证的本地提交，但必须明确报告未上传状态。

## 非目标

- 自动合并 PR 或自动上线生产；
- 支持 macOS/Linux；
- 将真实项目配置共享给其他用户；
- 本次直接提交 Universal Plugin Directory；
- 在安装脚本中管理或存储 GitHub/Codex 凭据。
