# 全局研发交付编排 Plugin 设计

## 1. 文档状态

- 设计日期：2026-07-28
- 目标用户：当前 Windows 用户 `JoySun`
- 部署范围：单机、个人、全局安装
- 首个接入项目：ExampleProject 后端
- 自动化终点：`READY_TO_MERGE`
- 正式发布：独立、显式触发的第二阶段
- 当前状态：核心设计已在对话中批准；等待书面规格审查

## 2. 背景

当前研发流程包含需求描述、方案确认、开发、测试环境部署、验收、创建 PR、代码 Review、修改 Review 意见、合并和正式发布。现有本地 Skills 已覆盖多个单点环节，但缺少统一、持久、可恢复的流程控制面，导致：

- 不同 Skill 之间没有统一状态和产物契约。
- commit、push、创建 PR 等动作被拆成大量人工确认。
- 部署、CI 和 Review 跨越较长时间，单次对话难以可靠保持状态。
- sub-agent 能执行局部工作，但不能单独承担跨会话、跨外部事件的流程持久化。
- 失败后容易依赖自然语言上下文判断是否重试，缺少幂等和远端事实对账。

## 3. 目标

建立一个全局个人 Plugin，将通用研发交付流程实现为可恢复状态机，并通过 Codex Skills、sub-agent、Python CLI、SQLite、Git/GitHub 和 Windows Task Scheduler 协作完成以下目标：

1. 用户通过 `$change-delivery` 启动完整交付流程。
2. 方案批准后，自动推进到 PR 满足合并条件。
3. 自动完成隔离开发、本地验证、内部 Review、提交、推送、Draft PR、测试环境部署、验收、CI 和外部 Review 修复循环。
4. 在 Codex CLI、电脑或对话中断后恢复。
5. 将人工介入集中在方案变化、高风险操作、无法自动解决的问题、PR 合并和正式发布。
6. 所有状态迁移均由结构化证据驱动，不能依赖 sub-agent 的自然语言完成声明。

## 4. 非目标

第一版不包含：

- 团队或多用户安装、中央权限管理和跨机器同步。
- 一个 run 同时修改多个仓库。
- 自动合并 PR。
- 自动执行正式环境发布。
- 自动直接写入测试或生产数据库。
- 自动执行真实支付、真实发信或其他不可逆第三方操作。
- 对任意未注册仓库执行 commit、push 或部署。
- 修改、废弃或覆盖现有本地 Skill。
- 依赖现有 ExampleProject Skill 才能运行。

## 6. 核心组件

### 6.1 `$change-delivery` Skill

这是完整交付流程的唯一公开入口，负责：

- 识别或要求用户选择已注册项目。
- 收集需求、约束和成功标准。
- 生成需求、设计和实施计划候选内容。
- 获取方案批准。
- 调用状态机推进当前 run。
- 将需要推理的有界任务交给 sub-agent。
- 向用户报告审批、阻塞和最终结果。

普通代码问题不能隐式触发完整交付流程。

### 6.2 Python CLI 内核

模块入口：

```powershell
python -m change_delivery <command>
```

公开应急命令：

```text
status
resume <run-id>
cancel <run-id>
doctor
tick
release <run-id>
```

Skill 日常调用更细粒度的内部命令；用户通常不需要直接操作。

### 6.3 项目注册表

只有显式注册的项目可以启用有副作用的自动化。项目配置至少包含：

- 稳定的 `project_id`。
- 仓库绝对路径。
- 允许的 remote。
- 远端基准分支。
- 功能分支命名规则。
- 共享测试分支。
- 版本接口及 Git SHA 字段路径。
- PR 前必过命令。
- GitHub 仓库标识和 required checks。
- 测试环境验收适配器。
- 凭据引用名称。
- 禁止的外部副作用。
- 正式发布默认关闭。

项目命令使用 `executable` 和 `args` 数组表达，禁止保存任意 PowerShell 字符串。

项目配置每次加载都进行 Schema 校验并计算配置哈希。活跃 run 发现配置哈希变化时进入阻塞状态，不能自动采用新配置。

## 7. 运行产物与批准快照

每个 run 使用唯一 run ID，并创建：

```text
runs/<run-id>/
├── requirement.md
├── design.md
├── implementation-plan.md
├── approval.json
├── evidence/
├── reports/
└── sanitized-summary.md
```

`approval.json` 记录：

- 项目 ID 和配置哈希。
- 需求、设计和计划的 SHA-256。
- 用户批准时间和当前 Windows 用户。
- 允许自动推进的终点。
- 已批准的副作用范围。
- base 分支及批准时的远端 SHA。
- 测试分支、remote 和 GitHub 仓库。

`ApprovalSnapshot` 是不可变审计快照，不是加密签名。Task 6 的状态门禁必须把显式批准事件与该快照绑定；本阶段不引入或假定任何签名密钥。
`AWAITING_DESIGN_APPROVAL → APPROVED` 只能在 `approval.json` 已原子保存后执行：
编排器计算该文件严格的 64 位小写 SHA-256，登记 `kind=explicit_approval` 且哈希相同的
`EvidenceRef`，再把预期快照哈希和证据引用传给状态机。仅提供证据 kind、自然语言批准
摘要或未绑定快照的批准事件均不能进入 `APPROVED`；批准证据 ID 与状态事件必须在同一
SQLite 事务中保存。

批准只覆盖同一 run 目录中的 `requirement.md`、`design.md` 和 `implementation-plan.md` 三个普通文件。生成和验证快照时拒绝链接或 reparse point，并在单次读取前后核对文件 identity、大小和修改时间。`verify_approval()` 表示一次时点检查，不能保证返回后文件永不变化；Task 10 的消费者必须只使用已批准 run 的这三个工件，并在每个外部副作用前重新验证批准快照。

以下变化使原批准失效：

- 需求范围或外部行为改变。
- 架构边界改变。
- 数据库结构或迁移策略改变。
- 权限、安全策略或外部副作用扩大。
- 验收成功标准降低或改变。

不改变行为的局部实现细节可以在批准范围内调整。

## 8. 状态机

### 8.1 主状态

```text
DRAFT
AWAITING_DESIGN_APPROVAL
APPROVED
PREPARING_WORKTREE
IMPLEMENTING
LOCAL_VALIDATION
INTERNAL_REVIEW
COMMITTING
PUSHING_FEATURE
PR_DRAFT
DEPLOYING_TEST
ACCEPTANCE_TESTING
PR_READY_FOR_REVIEW
MONITORING_CI_REVIEW
FIXING_CI_REVIEW
READY_TO_MERGE
MERGED
CLEANING_LOCAL
COMPLETED
```

### 8.2 中断状态

```text
BLOCKED
ENVIRONMENT_PREEMPTED
REVIEW_DECISION_REQUIRED
FAILED_TERMINAL
CANCELLED
```

### 8.3 状态迁移原则

- 每次迁移必须在 SQLite 事务中保存来源状态、目标状态、事件、证据引用和时间。
- sub-agent 的自然语言摘要不能直接推进状态。
- 任何新 commit 都会使绑定旧 SHA 的 CI、测试环境验收和 Review 证据失效。
- 恢复时必须先读取 Git、GitHub、测试分支和版本接口的真实状态，再决定是否继续。
- 对可能已经成功但客户端超时的写操作，先查询远端状态，不能直接重放。
- 进入 `BLOCKED` 或 `REVIEW_DECISION_REQUIRED` 时，来源状态必须随迁移事件持久化；恢复时由 Task 10 编排器从事件读取该来源并传给状态机，恢复目标必须与来源状态完全一致。
- 中断来源只能是正常的非终态主状态，不能是 `BLOCKED`、`ENVIRONMENT_PREEMPTED`、`REVIEW_DECISION_REQUIRED` 或任一终态。本约束复用既有事件记录，不新增数据库列。

## 9. Git 与 worktree 流程

### 9.1 基准分支

- 使用项目注册表中的远端基准分支。
- 启动时执行 fetch 并记录远端 SHA。
- 不使用本地同名分支作为基准。
- 只有显式要求其他基准、远端不存在或需求来自已有分支时才暂停。

### 9.2 原工作区

- 原工作区允许存在未提交改动。
- 编排器只记录状态，不读取这些改动作为需求输入，不修改、不暂存、不提交。
- 新 worktree 严格从已刷新的远端基准 SHA 创建。
- 分支名、worktree 路径冲突或 Git 元数据异常会阻塞流程。

### 9.3 提交策略

- 开发阶段形成少量原子 commit。
- PR 创建后禁止 rebase、amend 和强推功能分支。
- Review 修复使用独立 commit。
- 功能分支只允许普通 push。
- 每个自动 commit 关联 run ID、验证证据和来源阶段。

### 9.4 base 更新

- PR 不要求最新 base 且仍可合并时，不主动同步。
- GitHub 要求更新或 PR 无法继续时，自动 merge 最新远端 base。
- 禁止自动 rebase。
- 无冲突时重新执行所有失效门禁；有冲突时暂停等待人工决策。

## 10. 测试环境部署

ExampleProject 测试环境由共享远端 `test` 分支驱动。

部署命令必须使用带 SHA 约束的 lease：

```text
git push <frozen-push-url> HEAD:refs/heads/test --force-with-lease=refs/heads/test:<observed-sha>
```

禁止使用无条件 `-f`。

部署流程：

1. fetch `origin/test` 并记录当前 SHA。
2. 获取本项目的本机测试环境锁。
3. 使用精确 lease 推送当前功能 SHA。
4. 确认远端 `test` 指向目标 SHA。
5. 轮询版本接口，确认测试环境返回同一 SHA。
6. 验收过程中持续检查远端 `test` 和版本接口 SHA。

如果其他开发者覆盖 `test`：

- 当前验收立即失效。
- run 进入 `ENVIRONMENT_PREEMPTED`。
- 不抢回测试环境。
- 环境空闲后重新部署并从头验收。

验收完成后不自动恢复 `test`，保留最后一次成功验收版本。

## 11. 测试环境验收边界

默认允许：

- 通过公开 API 创建带 `codex-<run-id>` 标记的临时数据。
- 清理本 run 明确创建并可精确识别的临时数据。
- 读取测试环境 API、WebSocket、容器日志和只读数据库结果。
- 运行确定性测试和有界状态轮询。

默认禁止：

- 直接写数据库。
- 真实发信。
- 真实支付。
- 生产模型的高成本调用。
- 不可逆第三方操作。
- 修改真实用户或未标记业务数据。

特殊场景需要新审批，并使当前自动批准范围暂停。

## 12. PR、CI 与 Review

### 12.1 PR 生命周期

1. 本地必过检查成功。
2. push 功能分支。
3. 创建 Draft PR。
4. CI 与测试环境部署、验收可以并行。
5. 内部 Review 和必要修复完成。
6. CI、验收和内部 Review 通过后，将 PR 转为 Ready for review。
7. 监控外部 Review 和 CI，自动处理已授权范围内的问题。

### 12.2 自动修复范围

允许自动处理：

- 明确 bug、测试缺失、类型错误、lint 和 CI 失败。
- 不改变已批准需求的局部实现改进。
- 修复后的测试、commit、push 和 Review 回复。

必须暂停：

- 需求或架构改变。
- Review 意见互相冲突。
- 意见在当前代码中不成立。
- 迁移、权限、安全或不可逆数据行为发生变化。
- 同一问题连续两轮自动修复仍未解决。

### 12.3 `READY_TO_MERGE`

必须同时满足：

- PR base/head 与 run 记录一致。
- PR head SHA 与最近一次验证 SHA 一致。
- required checks 全部成功。
- 测试环境运行同一 SHA且验收有效。
- 内部规格、质量和专项 Review 通过。
- 可执行外部 Review 意见已处理。
- 没有未解决 Review thread。
- 仓库要求审批时，GitHub review decision 为 `APPROVED`。
- GitHub 报告可合并且没有冲突。
- 没有未处理的 Critical 或 Important 风险。

Plugin 不自动合并 PR。

## 13. sub-agent 模型

### 13.1 并发

- 主 Agent 负责状态、批准和最终决策。
- 同一 worktree 同时只能有一个写代码的 Agent。
- 最多三个并行只读 sub-agent。
- 规格、代码质量、安全/并发 reviewer 可以并行。
- reviewer 只返回意见，不直接修改代码。
- 所有修改统一交给单个实现 Agent。

### 13.2 结构化输出

每个阶段定义 JSON Schema，至少包含：

```json
{
  "status": "passed",
  "summary": "阶段摘要",
  "evidence": [],
  "findings": [],
  "next_action": "下一动作"
}
```

规则：

- Schema 校验失败时只允许重新格式化一次。
- 重新格式化不能重放有副作用操作。
- `passed` 必须引用实际命令、Git SHA、部署 SHA、测试报告或 Review 证据。
- 主编排器独立验证关键证据。

## 14. Windows Task Scheduler

定时任务运行策略：

- 当前用户登录时运行。
- 不使用管理员权限。
- 隐藏 PowerShell 窗口。
- 活跃 run 默认每 5 分钟检查一次。
- 无活跃 run 时不访问 GitHub、不执行项目命令。
- 24 小时无新事件后降频为每 30 分钟。
- 72 小时未完成则停止自动处理并生成超时摘要。
- 使用全局锁避免重入。
- 电脑休眠后，在恢复时执行一次补偿检查。

执行分两级：

1. `change_delivery tick` 确定性读取 SQLite、Git、GitHub、CI 和远端状态。
2. 发现已授权且需要推理的动作时，在对应 worktree 中启动受限 `codex exec`。

后台 `codex exec` 允许：

- 诊断并修复 CI。
- 处理已授权的 Review 意见。
- 运行测试、Review、普通 commit 和 push。

后台 `codex exec` 禁止：

- 正式发布。
- 数据库直写。
- 需求或架构变更。
- 破坏性清理。
- 扩大既有授权。

## 15. 重试、幂等与熔断

- 网络、GitHub 查询和健康接口抖动：指数退避，最多三次。
- 部署尚未完成：确认测试分支仍为目标 SHA 后继续轮询，不重复 push。
- 环境被抢占：等待后重新部署并完整验收。
- 测试或 CI 失败：先诊断，只有实际修改后才重跑。
- 同一 Review 问题最多自动修复两轮。
- push、PR 创建和 Review 回复超时：先查询远端是否已成功。
- 权限错误、未知错误和数据一致性问题：立即暂停。

所有写操作使用稳定的幂等键或可查询远端身份：

- run ID。
- 分支名。
- PR head/base。
- commit SHA。
- Review thread ID。
- 状态迁移事件 ID。

## 16. 命令与凭据安全

### 16.1 命令执行

- 默认使用参数数组调用子进程。
- 禁止 `shell=True`、`Invoke-Expression` 和任意 `cmd /c`。
- Git、GitHub 和部署操作由固定适配器生成参数。
- 项目注册必须显式提供 `remote_fetch_url` 与 `remote_push_url`；配置哈希绑定这两个不可变远端身份，不能在运行时静默采信仓库当前 URL。
- `remote` 名称只用于审计和远端跟踪引用命名。实际 fetch、push 与远端 SHA 核验直接使用注册时冻结的 URL。
- Git 的 `remote.<name>.url/pushurl` 是多值配置；command-scope `-c` 只会追加高优先级值，不能可靠清除竞态期间写入的低层值。因此网络操作不得把可变 remote name 作为 repository 参数。
- 必须使用 Shell 的项目动作只能引用已注册、受信的脚本文件。
- 活跃 run 期间配置变化会阻塞流程。

### 16.2 凭据

- GitHub 使用现有 `gh auth` 或已连接的 GitHub App。
- SSH 只引用本机密钥路径。
- 测试账号和数据库密码使用环境变量或 Windows Credential Manager。
- 项目配置只保存凭据名称，不保存值。
- 日志和 SQLite 对 Header、Cookie、Token、密码及敏感 URL 参数脱敏。
- 缺少凭据时报告变量名称，不要求把密钥粘贴到聊天。
- 第一版不授予正式环境写凭据。

## 17. 本地验证门禁

项目启用完整自动化前必须定义 `required_pre_pr_checks`。

规则：

- 所有修改运行相关测试、lint、类型检查或编译。
- 修改共享 DTO、鉴权、事务、缓存、数据库、队列、配置或公共工具时扩大验证范围。
- 必过检查全部通过后才能 push 和创建 PR。
- 全量测试可以交给 CI，但 PR 必须说明本地未执行范围。
- 测试环境验收不能替代本地测试或 CI。
- 没有可执行测试的项目不能启用自动推进到 PR。

## 18. 取消、清理与保留

### 18.1 取消

`cancel` 只停止流程：

- 停止新任务并尝试安全终止当前子进程。
- 保留 worktree、分支、PR 和测试环境版本。
- 不关闭 PR、不删除分支、不恢复 `test`。
- 输出现存资源清单。

### 18.2 合并后清理

- `READY_TO_MERGE` 时保留 worktree。
- Scheduled task 检测到 PR 已合并后，确认 worktree 干净并核对远端状态。
- 自动删除干净的本地 worktree 和已合并本地分支。
- 默认不删除远端功能分支。
- PR 关闭但未合并时不自动清理。

### 18.3 数据保留

- SQLite 的状态、批准、Git SHA、PR 和测试结论长期保留。
- 原始命令、CI 和验收日志保留 30 天。
- Markdown 汇总和脱敏证据保留 180 天。
- `pinned` run 永久保留脱敏报告。
- 清理仅作用于已终结 run 的已知文件；未知文件跳过。

## 19. 正式发布

正式发布与 Change Delivery 分离：

```text
Change Delivery → READY_TO_MERGE
人工合并
Production Release → 显式 release → 正式发布 → 发布后验证
```

第一版：

- 实现正式发布状态和只读预检接口。
- 不配置正式环境写操作。
- 不自动触发 release。
- 后续项目级发布适配必须经过独立安全设计和批准。

## 20. 现有 Skill 策略

- 不修改、不废弃、不覆盖现有 Skill。
- 新 Plugin 使用全新 Skill 名称和结构化契约。
- 可以参考现有 Skill 的检查方法、脚本思路和安全规则。
- Plugin 运行时不依赖现有 Skill。
- 新旧 Skill 不使用相同名称，避免路由混淆。

## 21. 第一版 ExampleProject 接入

第一版仅接入 ExampleProject 后端，并通过只读发现完成项目注册：

1. 定位仓库、remote、远端基准分支和当前测试分支。
2. 读取项目测试、lint、类型检查和构建入口。
3. 核对 GitHub 仓库、required checks 和 PR 保护规则。
4. 核对版本接口返回 Git SHA 的字段路径。
5. 核对测试环境部署由 `origin/test` 强推触发。
6. 根据现有 ExampleProject Skill 重新实现 Plugin 内的验收、异步 Review 和环境只读检查。
7. 生成项目配置候选。
8. 运行 Schema 校验和全量 dry-run。
9. 用户确认项目注册结果后才启用真实副作用。

发现得到的路径、命令、URL 和字段路径属于项目注册数据，不写死在通用状态机中。

## 22. Plugin 自身验证

启用真实项目前必须通过：

### 22.1 单元测试

- 状态迁移合法性。
- 批准哈希失效。
- 配置 Schema 和哈希。
- 命令参数生成。
- 脱敏。
- 重试和熔断。
- 超时后远端对账。
- `READY_TO_MERGE` 判定。

### 22.2 临时 Git 集成测试

- 本地 bare remote。
- 脏原工作区和隔离 worktree。
- 功能分支普通 push。
- `test` 分支精确 force-with-lease。
- lease 冲突。
- 幂等恢复。
- 干净 worktree 清理。

### 22.3 ExampleProject dry-run

- 读取真实项目、GitHub 和环境只读状态。
- 输出将执行的命令、状态变化、Skill 和审批。
- 不创建分支、不 push、不创建 PR、不部署。
- dry-run 必须由适配器阻止副作用，不能只在展示层隐藏。

只有单元测试、模拟集成测试和用户审查的 dry-run 全部通过后，才能执行第一次真实 run。

## 23. 错误处理与通知

需要人工介入的状态：

- `AWAITING_DESIGN_APPROVAL`
- `BLOCKED`
- `ENVIRONMENT_PREEMPTED`
- `REVIEW_DECISION_REQUIRED`
- `READY_TO_MERGE`
- `FAILED_TERMINAL`
- `PRODUCTION_RELEASE_READY`

Codex CLI 输出必须包含：

- run ID。
- 项目和 PR。
- 当前状态。
- 阻塞原因或完成证据。
- 建议的下一动作。

相同状态不重复通知；只有状态或阻塞内容发生变化时再次提示。

## 24. 成功标准

第一版完成必须满足：

1. Plugin 可通过个人 Plugin 机制全局安装并被 `$change-delivery` 显式调用。
2. Python CLI 和 SQLite 可以创建、暂停、恢复、取消 run。
3. 重启 Codex 或电脑后可以根据 SQLite 与远端事实恢复。
4. ExampleProject 后端注册配置通过 Schema 和 dry-run。
5. 模拟仓库证明 worktree、普通 push、精确 lease 和幂等恢复正确。
6. 一次受控 ExampleProject 需求可以自动推进到 `READY_TO_MERGE`。
7. 测试环境验收绑定明确 Git SHA。
8. CI/Review 自动修复遵守两轮限制和批准范围。
9. 不修改或依赖现有 Skill。
10. 正式环境没有任何自动写入口。
