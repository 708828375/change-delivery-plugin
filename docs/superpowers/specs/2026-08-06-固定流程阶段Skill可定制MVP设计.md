# 固定流程、阶段 Skill 可定制的交付 MVP 设计

## 1. 背景

当前插件已经具备固定交付状态机、阶段执行器、Git/PR/测试环境适配器和证据登记能力，但用户仍可能需要反复调用 `resume` 来连接各阶段。同时，阶段个性化分散在内置 Skill 和项目配置中，commit、PR 等阶段缺少统一的内容定制入口。

本次改造的核心目标不是建设通用工作流平台，而是解决两个直接问题：

1. 方案批准后，各阶段能够由运行主机连续推进，只有真正需要人工决策时才暂停。
2. 每个业务阶段都有清晰的 Skill 个性化入口；Skill 负责内容和执行要求，运行主机负责权限、安全副作用、证据和状态。

## 2. MVP 范围

### 2.1 包含范围

- 保留现有固定阶段和固定状态流转。
- 增加单次连续推进能力，自动执行连续可运行状态。
- 为需要判断、生成内容或执行项目内工作的业务阶段提供默认 Skill。
- 为内部 Review 建立“Review、修改、本地验证、再次 Review”闭环。
- 内部 Review 自动修复默认最多 3 轮。
- PR 标题和正文由 `delivery-pr` 动态生成，运行主机校验后自动创建。
- 用户可通过修改插件内对应 `SKILL.md` 定制阶段行为。
- 继续使用运行主机作为 Git、PR、测试部署和验收副作用的唯一执行者。

### 2.2 不包含范围

- 不支持用户自由增加或删除阶段。
- 不支持用户自由定义状态图或状态流转表达式。
- 不支持多个 Skill 合并、优先级覆盖和冲突解析。
- 不支持项目级自定义 Skill 注册表。
- 不自动合并 PR。
- 不执行生产环境写操作；`production-release` 仍只执行只读预检。

## 3. 设计原则

### 3.1 Skill 决定阶段内容

Skill 可以定义阶段的分析方式、输出格式、编码规范、测试补充要求、Review 维度、commit message 和 PR 文案。Skill 只能在运行主机注入的审批范围和权限内工作。

### 3.2 运行主机决定安全执行

运行主机负责：

- 选择当前阶段和对应 Skill；
- 注入可信需求、审批产物、Git SHA、测试证据和受限外部数据；
- 设置只读或可写 sandbox；
- 校验 Skill 输出 Schema 和状态；
- 执行 Git、PR、测试环境等确定性副作用；
- 校验远端 SHA、幂等身份和权威证据；
- 推进状态、恢复中断并限制自动重试次数。

Skill 不得直接改变状态数据库，不得绕过运行主机执行敏感副作用，也不得扩大已批准范围。

### 3.3 纯机械状态不调用 Skill

准备目录、记录状态、轮询平台、验证远端 SHA 等没有内容定制价值的机械状态由运行主机直接处理，避免额外模型调用和不确定性。

## 4. 阶段、Skill 与运行主机职责

| 阶段 | 默认 Skill | Skill 职责 | 运行主机职责 |
|---|---|---|---|
| 交付入口 | `change-delivery` | 理解需求，引导启动或恢复运行 | 检查项目登记、创建运行、读取当前状态 |
| 方案设计 | `delivery-planning` | 生成 `design.md` 和 `implementation-plan.md` | 限制写入范围、记录产物 hash、进入审批状态 |
| 方案确认 | 无 | 无 | 生成审批快照并校验用户确认的 hash |
| 准备开发环境 | 无 | 无 | 校验仓库和分支，准备受控开发目录 |
| 开发实现 | `delivery-implement` | 按批准方案和用户要求修改代码 | 控制写入范围，记录准确代码树证据 |
| 本地验证 | `delivery-local-validation` | 执行允许的补充检查并分析失败 | 执行权威 `required_pre_pr_checks`，绑定被测 SHA |
| 内部 Review | `delivery-review` | 对准确代码树执行只读 Review | 限制只读，校验 Review 结果和树身份 |
| Review 修改 | `delivery-review-fix` | 只修改本轮可执行 Review 或 CI 问题 | 注入受控问题范围，记录修复轮次和新代码树 |
| commit 内容生成 | `delivery-commit` | 生成符合用户要求的 commit message | 校验内容，执行 `git commit`，记录 commit SHA |
| 推送功能分支 | 无 | 无 | 普通 push 并验证远端 SHA，禁止强推功能分支 |
| PR 内容生成 | `delivery-pr` | 根据需求、diff 和证据生成 PR 标题、正文 | 校验、脱敏、自动创建 PR 并防止重复创建 |
| 测试部署准备 | `delivery-test-deploy` | 执行允许的部署前检查并返回就绪结果 | 按 `test_push_strategy` 推送登记的测试分支并校验 SHA |
| 测试环境验收 | `project-test-acceptance` | 执行验收场景、断言和精确清理 | 独立执行 `acceptance_check`，校验部署 SHA 和清理证据 |
| PR 转正式 Review | 无 | 无 | 将 Draft PR 转为 Ready 并记录平台证据 |
| CI/外部 Review 监控 | 无 | 无 | 读取 CI、Review 状态和评论，识别待修改问题 |
| 外部 Review 修改 | `delivery-review-fix` | 处理可信化后的 CI 和 Review 问题 | 将评论放入 `untrusted_data`，限制修改范围和次数 |
| 合并前检查 | `delivery-ready-check` | 汇总改动、测试、Review 和风险 | 校验权威证据并决定是否进入 `READY_TO_MERGE` |
| 合并 | MVP 不执行 | 无 | 停在 `READY_TO_MERGE`，等待显式授权和后续能力 |
| 生产发布 | `production-release` | 生成发布预检说明 | 只读预检，始终拒绝生产写操作 |

## 5. 内部 Review 闭环

内部 Review 不得在发现可执行问题后直接进入 commit。固定闭环为：

```text
开发实现
  -> 本地验证
  -> 内部 Review
      -> 通过：commit
      -> 有问题：Review 修改
          -> 再次本地验证
          -> 再次内部 Review
```

约束如下：

- `delivery-review` 始终只读。
- `delivery-review-fix` 只能处理本轮明确的可执行问题。
- 修改后必须对新代码树重新执行本地验证。
- 本地验证通过后必须重新 Review，旧 Review 证据不能复用于新代码树。
- 每次进入 Review 修改时消耗一轮自动修复次数。
- 测试失败后的当前轮修复不额外消耗 Review 修复次数。
- 默认最大内部 Review 自动修复次数为 3，可由受信任项目配置收紧或调整到运行主机允许的范围。
- 超过上限、问题互相冲突或需要扩大批准范围时，进入 `REVIEW_DECISION_REQUIRED`。

## 6. PR 内容生成与创建

`delivery-pr` 只生成内容，不直接访问 Git 平台。运行主机向其提供批准产物、准确 diff 摘要、commit SHA 和测试证据，并要求返回受限结构：

```json
{
  "title": "PR 标题",
  "body": "PR 正文"
}
```

运行主机必须：

- 校验标题和正文非空且大小受限；
- 对凭据、token 和敏感字段进行脱敏或拒绝；
- 绑定当前审批范围、功能分支和准确 commit SHA；
- 忽略 Skill 输出中夹带的命令、授权请求或状态指令；
- 使用幂等身份自动创建一次 Draft PR；
- 保存 Skill 内容 hash、输入事实 hash、生成结果、PR 地址和平台返回身份作为证据。

校验通过后自动创建 PR，不增加人工确认关卡。生成或平台调用失败时进入可恢复阻塞状态。

## 7. 连续推进

运行主机应提供面向单次运行的连续推进操作。该操作循环调用现有单步状态机，每次重新读取持久化状态，并在达到暂停条件时返回统一结果。

暂停条件包括：

- `AWAITING_DESIGN_APPROVAL`；
- `BLOCKED`；
- `REVIEW_DECISION_REQUIRED`；
- `READY_TO_MERGE`；
- `COMPLETED`、`FAILED_TERMINAL` 或 `CANCELLED`；
- 当前状态需要等待外部 CI、Review 或其他尚未就绪事实。

连续推进必须设置单次最大步数，防止状态机缺陷导致无限循环。每一步仍使用现有幂等操作身份、状态 compare-and-swap 和证据登记，不另建第二套状态逻辑。计划任务继续负责等待型状态的后续协调。

## 8. Skill 契约

每个阶段 Skill 必须明确：

- 触发阶段和输入事实；
- 允许执行的动作；
- 禁止执行的动作；
- 返回结果 Schema；
- `passed`、`failed`、`blocked` 的使用条件；
- 不可信外部数据边界；
- 缺少运行主机契约时必须阻塞，不得猜测。

运行主机始终注入权威 Schema、状态映射和允许/禁止动作。用户修改 Skill 可以改变阶段做法和内容格式，但不能改变这些硬性契约。

## 9. 个性化与安装边界

MVP 允许用户直接修改插件源码中的阶段 `SKILL.md`。重新安装时，安装器将经过校验的 Skill 复制到隔离运行主机。运行中的阶段只使用运行主机批准注册表中的 Skill，不读取任意项目文件夹或用户全局 Skill。

本阶段不实现项目级 Skill 覆盖。若实际使用证明直接修改内置 Skill 会造成升级冲突，再单独设计“内置安全契约 + 项目自定义 Skill”机制。

## 10. 失败与恢复

- Skill 返回格式无效时，沿用受限的一次格式修复；仍无效则阻塞。
- 确定性命令失败时保存命令身份和脱敏结果，不伪造成功证据。
- 进程超时、依赖不可用和平台暂时失败进入可恢复状态。
- 环境 SHA 变化时继续使用 `ENVIRONMENT_PREEMPTED`，不得接受部分验收结果。
- 重启后根据持久化状态、幂等身份和平台事实继续，不重复副作用。

## 11. 测试与验收标准

至少覆盖：

- 连续推进能跨越多个成功状态并在所有暂停状态停止；
- 连续推进有最大步数保护，且不复制状态转换逻辑；
- 每个业务阶段加载准确的默认 Skill；
- Skill 缺失、Schema 不匹配或越权时阻塞；
- 内部 Review 问题触发修改、本地验证和再次 Review；
- 新代码树不能复用旧测试或旧 Review 证据；
- 第 3 轮仍未通过时进入 `REVIEW_DECISION_REQUIRED`；
- `delivery-commit` 只能生成 message，不能直接执行 Git；
- `delivery-pr` 输出经校验后只创建一个 PR；
- PR 生成失败、敏感信息或平台失败不会推进状态；
- 测试强推继续只使用登记的 `test_push_strategy` 和测试分支；
- 外部 Review 内容继续位于 `untrusted_data` 边界；
- 到达 `READY_TO_MERGE` 后停止，不自动合并或发布生产。

## 12. 实施边界

实施应优先完成最小闭环：

1. 连续推进；
2. 内部 Review 修复闭环；
3. 新增阶段 Skill 和运行主机契约；
4. commit 内容生成；
5. PR 内容生成和自动创建；
6. 测试部署准备与合并前汇总 Skill；
7. 安装、发布和完整回归。

不在实施过程中顺带引入自由状态机、通用工作流 DSL 或项目级 Skill 组合。
